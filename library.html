15 — Library

46 of 58, and what that does not mean.

Thirty-two more components, taking coverage from 24% to 79%. The inventory below is published in full so the figure can be audited rather than trusted — and the first section says plainly why a component count is a weak measure of readiness.

What 46 of 58 means

What genuinely improved

  • A team can now build most enterprise screens without leaving the system. That was not true at 14.
  • The dot-rail primitive extended to pagination, the nav rail and the timeline — each is options along a line, so none of them needed a new indicator invented for it. It extended to five of thirty-two on the first pass, which was not enough.
  • Every new component consumes semantic tokens only, works in both themes and all three densities, and has a forced-colors path.
  • The enterprise and regulated profiles cover the new components too — the loop indicators fall back where the conservative profile requires it.

What did not move at all

  • No npm package, no TypeScript, no React binding. Still not installable.
  • No Figma library. Designers still cannot use any of this.
  • No RTL. Logical properties were used throughout this batch, which helps — the earlier components still need converting.
  • No VPAT, no screen-reader test matrix. Every accessibility claim here is still unverified by testing.
  • Still unfunded. The question an enterprise asks first is whether this exists in three years.
Component count is a weak proxy for readiness, and worth saying out loud while raising it. Coverage went from 24% to 79%; the honest readiness assessment barely moved, because four of the six remaining blockers are engineering and organisational rather than design. A library of forty-six components that cannot be installed is not more adoptable than a library of fourteen that cannot be installed. The gap analysis is updated to reflect exactly this.

The derivation audit

Which components are actually kolam, and which are ordinary components wearing Tamil-named tokens. The deletion test, run on each of the forty-seven individually.

The first pass of this batch failed the test. Of the thirty-two components added, five carried the line and twenty-seven were conventional components consuming semantic tokens. That is the same failure as the original token layer — a kolam-shaped vocabulary wrapped around a system that would have looked identical without it — repeated one level down, in the components rather than the tokens. It was found by grepping the stylesheet for the primitive's four CSS signatures, not by reading the code, because reading your own code is how you miss this.

Three categories, not two

The binary "kolam or not" hid the interesting case. A component can carry a kolam mark that does no work — which is decoration, and worth admitting rather than counting.

Derived — 21

State or structure is carried by the line. Delete the kolam and the component loses information, not character. These are the ones that justify the source.

Ornamented — 3

Carries a kolam mark that carries nothing. Delete it and the component still works; only the flavour goes. Honest decoration, labelled as decoration.

Conventional — 23

A standard component consuming semantic tokens. There is no kolam in a scrim or a skeleton and inventing one would be worse than leaving it alone.

Why the number should not be higher

Forty-five percent is not an embarrassment to be fixed. A scrim is a translucent rectangle; a skeleton is a shimmering block; a tooltip is a small box near a thing. There is no kolam reading of these that is not a costume. The test each derived component passed is narrow and worth stating:

  • Is it options along a path? Tabs, pagination, breadcrumb, nav rail, timeline, menu, slider, stepper. The kolam line visits dots in order; so do these.
  • Is it a thing that opens and closes? Radio, checkbox, accordion, file upload, tag, status. The line either wraps a dot or passes it, and there is no third option.
  • Is it a line in motion, or a line at rest? Progress and meter. Once that distinction is carried by the presence of a head loop, the two components stop needing different colours to be told apart.

Everything that failed all three was left alone. Forcing the language onto a dialog would have produced exactly the thing you objected to two rounds ago: kolam as a skin.

The deletion test, applied to this page. Remove the kolam from the twenty-three conventional components and nothing is lost. Remove it from the twenty-one derived ones and the system loses its greyscale-safe state language, its distinction between progress and meter, its sort indicator, and every selected state that currently survives Windows High Contrast Mode without a colour. That asymmetry is the whole argument, and it is why the ratio is published rather than the headline.

Counting rule. Partial does not count toward the headline figure — the conservative reading is the honest one. 46 shipped + 4 partial + 8 absent = 58. The headline is therefore 46 of 58 = 79% fully shipped, or 86% if you allow the partials, which this page does not.

The four partials each name their limit: the data grid has no cell editing, grouping or server-side data; the menu, popover and tooltip use naive viewport-flip placement rather than Floating UI, so they will misplace inside scrolling containers or transformed ancestors. The eight absent are combobox, multiselect, date picker, tree view, command palette, charts, notification centre and the mobile sheet.

This callout originally claimed "46 shipped + 4 partial = 46", which is wrong by four. The audit script that checks the table against the headline caught it — which is the argument for publishing the inventory in a machine-checkable form rather than asserting a percentage.

    Placement is the naive version. Menus, popovers and tooltips flip against the viewport edge and clamp horizontally.
